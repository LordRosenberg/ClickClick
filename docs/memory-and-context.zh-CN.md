# 记忆与上下文管理

[架构与详设索引](architecture.zh-CN.md#模块设计文档) · [English](memory-and-context.md)

**重要信息留得住，每次决策读得少，需要细节时找得到。** ClickClick 分别保存原始记录、工作笔记和结构化摘要，为模型组装当前任务所需的上下文。

## 模型每次看到什么

<!-- design-diagram:memory-assembly -->

![记忆与上下文：压缩、独立恢复与来源回查](assets/design-memory-assembly.zh-CN.svg)

压缩只替换较早过程。任务、计划与笔记独立恢复，摘要条目绑定原始来源；需要细节时回查，最近两步和当前观测继续服务执行。

[Mermaid 源码](diagrams/design-memory-assembly.zh-CN.mmd)

<!-- /design-diagram:memory-assembly -->

原始指令提供目标和用户约束，Planner 提供当前阶段与计划，运行时提供预算和最新观测。笔记保存后续所需的信息，摘要衔接较早的执行过程，各自独立维护。

Planner 读取任务级目标、阶段与决策记忆；Executor 组合当前阶段、最新观测、近期完整执行历史和适用技能；Reviewer 围绕争议与证据独立判断。原始需求／用户变更、计划、预算、笔记和技能各自进入上下文，不依靠摘要复制它们。摘要仅概括较早过程，历史检索按需补足细节。

## 笔记：带走后面需要的信息

Executor 在信息**后续需要、可能离开上下文、尚未充分保留**时写笔记。例如，跨应用录入前保存地址；普通点击、已无后续影响的错误和重复失败明细留在原始历史中。仍影响未完成任务的方法失败，应保留其适用范围与实际结果，避免仅因界面恢复可用就丢掉仍有效的障碍；这不构成永久重试禁令。

| 内容 | 用途 | 更新方式 |
| --- | --- | --- |
| 正文 | 保存完整数据、顺序、来源和必要的不确定性 | 同一主题更新同一 `note_key`，旧版本保留 |
| `retained` | 选出后续决策要直接看到的短内容 | 非空值设置；省略或 `null` 保持原值；空字符串清除 |
| `unresolved` | 标记仍影响任务结果的实质问题 | 省略不会清除；以带说明和来源的解决记录关闭 |

`retained` 是正文的独立摘录：修改正文时，需要同步纠正或清除已失效的摘录。普通待办由计划管理，可选的进一步核验不自动成为未解决问题。

| 写入动作 | 版本与顺序 |
| --- | --- |
| 修改同一 key | 生成新版本，保留旧版本 |
| 完全相同的覆盖 | 不增版本、不刷新时间 |
| 顺序追加 | 保留发生顺序，相同值的两次发生仍是两条 |

## 压缩：概括旧过程，保留近期原文

压缩由与 Executor 相同配置模型的独立会话完成，只提供摘要提交工具。图片不参与文字压缩，原始对话、截图和笔记版本仍可回查。

| 摘要栏目 | 保留什么 | 不写什么 |
| --- | --- | --- |
| `results` | 已观察结果、产物和必要的数据 | 把转述或候选写成已验证事实 |
| `decisions_and_attempts` | 影响后续选择的实际尝试、结果与范围 | 猜测原因、新增验证要求或重试禁令 |
| `critical_context` | 前两栏没有覆盖的必要历史细节 | 复制任务清单、当前计划或普通操作日志 |

每条摘要关联来源。压缩会话使用短标签，运行时将它们还原为持久引用；执行模型平时阅读简短正文，缺少细节时通过 `summary_source` 回查摘要及原始记录。

**去重只影响展示。** 摘要条目与本次已提供笔记的版本、保留全文都相同时，隐藏摘要中的副本；笔记未被提供时，副本重新显示。存储中的内容不删除，也不按语义相似度合并。

| 压缩规则 | 行为 |
| --- | --- |
| 触发 | 历史超过预算，且摘要替换预计能释放空间 |
| 历史预算 | 默认 16,000 个估算 token；只计历史，不等于模型总窗口 |
| 近期保留 | 最近两个完整执行步骤及回执不压缩 |
| 摘要容量 | 目标 3,000 字符，硬上限 4,000，包含标题与分隔符 |
| 提交失败 | 普通压缩最多三轮模型调用（含首次），Jev enforce 最多两轮；有效提交前不替换活跃历史，不强行截断 |

ChatGPT 的历史预算可用 `CLICKCLICK_CHATGPT_HISTORY_TOKENS` 设置；显式模型／角色预算优先。预算越高，原文保留越多，每次请求的上下文成本也越高。

### 主要配置

| 配置 | 默认／作用 |
| --- | --- |
| `CLICKCLICK_EXECUTOR_CONTEXT_TOKENS` | `16000`，Executor 历史压缩阈值 |
| `CLICKCLICK_CHATGPT_HISTORY_TOKENS` | 可选，ChatGPT 通道历史预算 |
| 模型配置 `context.executor.history_tokens` | 显式模型／角色覆盖历史阈值 |
| 模型配置 `context.max_input_tokens` | 可选，估算完整请求容量；不是历史预算 |

完整请求还包含提示词、阶段、记忆、工具和图片。阈值与图片估算不等于提供方计费 token；缓存、压缩和额外回查要合计比较。近期保留、笔记与摘要容量由协议固定，具体定义见[摘要实现](../agent/revisable/summary.py)与[任务存储](../agent/revisable/store.py)。

## 可选 Jev 文字忠实度校验

默认 `CLICKCLICK_JEV_MODE=off`；可选 `shadow` 记录判断，`enforce` 参与摘要接纳。Jev 只检查文字是否忠实于原始来源，不读取图片像素，也不替模型证明业务结论。摘要继承引用必须追到原始记录，旧摘要不能证明自身正确。

### 接入位置与输入证据

检查发生在压缩模型提交候选摘要之后、Harness 接纳摘要并替换活跃历史之前。运行时先解析每条摘要绑定的持久引用，再将主张与完整原始文字交给 Jev。例如，来源只记载“准备发送邮件”或派发成功、效果未知时，摘要不能写成“邮件已经发送”。

来源包括观测中的树／文字、带角色归属的模型报告、工具调用与结果，以及被引用的笔记版本、计划、事件和测量。任务要求可以证明“需要完成什么”，不能证明“已经完成”；模型报告可以作为该报告的来源，不能自动升级为独立观测事实。全文保留用于解释代词、否定、归属和范围，来源超限明确标为无法校验，不截断证据后宣称通过。

### 使用哪些概率，分别承担什么职责

当前 `facets` 路径先检查整句与原文连续子句，再获取关系／错误类型诊断与适用的细节判断。

| 输出 | 问题与分数含义 | 当前用途 |
| --- | --- | --- |
| 忠实度 Noul | 针对一个是非问题返回成立分数：整句、子句或明确目标细节是否得到来源支持。记作 `p_faithful`，错误分数为 `1 - p_faithful` | 接纳与修订的主要判定依据 |
| 关系 Choice | 对来源与主张给出 `supports / contradicts / says_nothing` 的关系概率及置信信息 | 辅助解释支持、矛盾或依据不足；不在当前 facets 策略中单独触发修订 |
| 错误类型 Noul | 分别询问是否存在新增事实、范围扩大、归属变化、确定性升级、尝试变成功。这里高分表示该错误存在，与忠实度 Noul 的方向不同 | 定位原因和组织修订反馈；类型可以重叠，高类型分数不单独推翻忠实度判定 |

关系类别互斥，五类错误可以同时存在；各分数按所回答的问题使用，不当作统计独立事件相乘。当前定向细节提取覆盖有限的成员选择、英文／ISO 绝对日期和已确认效果等表达，不代表所有人数、日期或中文表述都有专用细节题；其余仍由整句／子句检查覆盖。

### 多个概率怎样最终决定是否修订

由 Harness 的 `SummaryVerifier.policy()` 按以下优先级处理一条摘要，Jev 本身不直接改写正文：

1. **先检查覆盖与可用性。** 缺少来源、答案、必要细节分数，或服务／容量异常时，记录无法校验，进入后述降级策略；不能记成语义验证通过。
2. **再判断是否需要修订。** 任一原文子句的错误分数达到 0.88、多子句条目的整句错误分数达到 0.95，或适用的明确细节错误分数达到 0.74，即标记 `repair`。单句使用子句门槛；多个错误同时触发时合并问题片段。有限格式下发现明确整数加总自相矛盾，也可触发修订，该机械检查不代替一般事实或数学验证。
3. **未触发修订时判断能否验证。** 整句、子句及存在的细节忠实度判断全部达到 0.60，才标记 `pass / validated=true`。
4. **其余为语义灰区。** 完整检查没有达到修订门槛，也未达到全部支持门槛时，标记 `uncertain_bypass / validated=false`，可接纳但不额外花一轮修订；评测中漏过错误仍计漏检。

因此，一条错误子句不能被其他高支持分数抵消；Choice 的置信信息和五类错误类型用于诊断，不作为另一个平均分或独立否决票。旧 `relation` 策略的负向置信／类型门槛，以及历史长来源隔离组合的联立规则，属于不同策略，不能混入当前 facets 判定。

### 阈值怎样校准与冻结

校准对象是**应用判定规则**，没有拟合分数到真实正确率的映射。各门槛由开发样本搜索与具体误判修正共同确定，并非四个阈值都由同一次网格搜索得到。

- **样本与标签。** 从历史摘要和完整绑定来源构建开发记录，并构造受控错误，按原文核对标签与理由；标签不进入 Jev 输入。已查看并用于调整策略的留出样本转为开发回归。历史标签由代理审阅，未经独立人工裁决，后续勘误保留原报告。
- **子句门槛 0.88。** 历史脚本枚举 0.50～0.98、步长 0.02，另加 0.99，同时比较整句／子句聚合方式。先最大化精确率、召回率、准确率中的最小值，再比较 F1、准确率等，同分优先接近预设参考值 0.90。按当时标签，128 条可判定校准项中，0.86 与 0.88 均检出 15 条、误修 0 条、漏检 1 条；0.90 则漏检 4 条，因此按同分规则选 0.88。现行子句沿用该门槛，不能称其为唯一最优值。
- **复杂整句门槛 0.95。** 正确日期区间陈述曾得到 0.91 的整句错误分数，而子句没有达到拒绝门槛；因此提高整句拒绝门槛，减少弱整句否定引发的误修。这是误判驱动的保守选择，不是证明 0.95 全局最优。
- **明确细节门槛 0.74。** 17 条成员／日期开发项中，正确项最高错误分数为 0.68，错误项最低为 0.79，取中点 0.735 后使用 0.74。该间隔只描述这批开发样本。
- **支持门槛 0.60。** 早期关系判断实验中，正确校准项最低 Choice confidence 为 0.63，候选网格的 0.60 可覆盖这些项，0.65 开始使部分正确项进入灰区。当前沿用该支持门槛，不宣称已对现行所有 Noul 判断重新统一寻优。
- **冻结后验收。** 固定标签、来源和阈值，再发送后续验收请求，不根据该批结果调参后继续称独立测试。20 条参数冻结验收中，4 条受控错误均触发修订，16 条正确项未误修，其中 4 条仅为未验证灰区；验收期间修过容量／缓存机械边界，因此不称全部代码冻结后的严格盲测。

样本按阶段分别记录：历史 facets 开发池 170 条，后续 32 条与 26 条已打开样本用于开发／回归；核心参数冻结验收为 20 条；后续长来源组合的 44 条是已知回归且包含此前样本。早期 relation 阶段另有 248 条已打开开发项，来源与策略不同。各轮不直接相加为“250 条独立真实轨迹评测集”，重复检查也不增加独立样本量。

网格搜索脚本、质量指标、各阶段校准及最终验收记录保留在开发仓库；本节给出当前判定规则、阈值依据和样本限制。有限回归成绩不等于生产可靠率，也不能单凭摘要检出结果宣称任务成功率提高。

### 修订、降级与复用边界

反馈给摘要会话的是错误片段、来源和原因，格式与语义共用一次修正；已接纳项保持正文与来源。修正仍失败时保留最后机械有效候选中的已接纳／未评估条目，排除已知拒绝项并保存审计，可能得到不完整甚至空摘要。原文和近期步骤仍保留。

相同完整来源集合合批，最多两批并发，共享 8 秒检查截止。默认 `CLICKCLICK_JEV_FAILURE_POLICY=bypass`：服务、容量或覆盖不足时提交机械有效但未验证的候选；服务故障按提供方／凭据冷却 60 秒，不增加修正调用。已有候选的压缩总时限为 90 秒。尚无机械有效候选、主模型认证／额度、存储失败与取消沿用原处理。严格实验可选 `rollback`，但原文也可能超过模型容量。

完整判断按任务、主张、原始来源／上下文和模型／问题身份缓存，阈值重新应用；失败不缓存为通过。来源上限、阈值等配置见[Settings](../shared/config.py)，具体历史校准与自然／受控错误结果见[历史实验](memory-context-experiments.zh-CN.md)。这是一项可选校验，不保证摘要无误。

## 存储：数据库、文件、内存各司其职

SQLite 保存当前状态、版本记录与索引；文件保存对话、图片和大正文；进程内存维护活跃工作副本。存储分工、发布完整性与备份见[Session 与存储详设](session-storage.zh-CN.md)。

### 如何找到同一条笔记，以及它的旧版本

**key 是笔记的名称，来源引用则指定“哪条笔记的哪个版本”。** 例如，模型要记住一个配送地址：

| 发生的事情 | 保存结果 | 回查用的来源引用 |
| --- | --- | --- |
| 首次记下“松林路 8 号” | 命名为 `delivery_address`，保存第 1 版 | `note:delivery_address@1` |
| 地址更正为“松林路 18 号” | 沿用同一个名称，保存第 2 版；第 1 版仍在 | `note:delivery_address@2` |
| 想确认最初记下的地址 | 按第 1 版的引用读取，得到“松林路 8 号” | `note:delivery_address@1` |

引用中的 `note` 表示笔记，`delivery_address` 是名称，`@1` 表示第 1 版。模型使用这个名称更新笔记，使用带版本的引用回读确切内容。

数据库还会记录所属任务，因此两个任务都可以有名为 `delivery_address` 的笔记，互不混淆。`note_key` 在数据库中称为 `record_key`；它是逻辑名称，不是数据库自动生成的行号。

对话文件的 `dialogue/<hash>.json` 则是磁盘路径：数据库用它找到 `artifacts/` 下的原始消息文件，与上述笔记引用是两种不同的定位方式。

## 回查：按需读取完整来源

| 需要什么 | 如何获得 |
| --- | --- |
| 当前保留内容之外的笔记 | 从笔记目录取得来源句柄，调用 `read_history` |
| 笔记全文及关联来源 | `read_history(source=…, full=true)` |
| 摘要的依据 | 读取 `summary_source`，再沿条目来源读取原始对话或观测 |
| 早先的画面 | 按观测来源读取图片；历史图片不作为当前点击坐标 |
| 不知道确切来源 | 字面关键词查询；无匹配不表示信息不存在 |

上下文按容量选取完整条目，标明省略；已知来源可直接回读，截断结果提供继续读取位置。内部追踪编号保存在记录中，日常正文只保留可用的读取／更新句柄。

### 容量参考

文本长度按字符计数，不是 token；条目数量单独标明。

| 内容 | 容量 |
| --- | --- |
| 普通笔记 | 64 个 key；每条正文 6,000 |
| 保留摘录 | 每条 600；整个注入包 3,000，包含元数据 |
| 未解决问题 | 最多 8 条；每条 400 |
| 笔记目录 | 每页预算 2,400 |
| Planner / Reviewer 的近期笔记、操作摘要 | 各自预算 12,000 |
| 工具测量 | 最多 4 条；预算 6,000 |
| 普通历史读取 / 指定来源全文读取 | 3,000 / 12,000 |
| 关键词查询 | 最多 6 条匹配记录 |

**能力边界：** 来源可追溯不等于结论正确。模型仍可能遗漏信息、保留过时判断或误用笔记；原始记录用于核对和纠正。持久保存也不等于任意中断都能无损恢复。
